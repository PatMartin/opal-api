# opal-api

[![Validate OpenAPI contracts](https://github.com/PatMartin/opal-api/actions/workflows/openapi-validate.yml/badge.svg)](https://github.com/PatMartin/opal-api/actions/workflows/openapi-validate.yml)

OpenAPI contracts and validation tooling for the OPAL suite: speech recognition, visual perception, reasoning, event routing, and speech synthesis.

This repository defines the HTTP interfaces that OPAL services and their clients agree to implement. It contains five OpenAPI 3.1 service specifications, a shared contract kernel, documentation, and automated checks. It is intended for service implementers, client authors, and contributors evolving the interfaces together.

The current service contracts and kernel are version **1.7.1**. These files describe required and optional service behavior; passing the checks here verifies the contracts, not a running implementation. Service servers, the `opal` command-line application, and a browser application are not implemented or generated by this repository's scripts.

## Capabilities

- **Reusable contract definitions:** services reference shared headers, errors, schemas, and route definitions rather than maintaining separate copies.
- **Consistent service management:** health, identity, settings, profiles, personas, backups, and process lifecycle routes appear across the suite.
- **Traceable requests:** four correlation headers connect HTTP exchanges and derived events across services.
- **Explicit concurrency and lifecycle semantics:** configuration changes use strong ETags; asynchronous admissions, terminal results, cancellation, and streaming behavior are documented separately.
- **Defined action execution boundary:** Think uses Event's registered actions and execution records, with a declared principal that can discover and invoke actions but cannot administer them.
- **Validation for authors and consumers:** structural linting, suite-specific lint rules, standalone bundles, schema fixtures, and contract regression tests run without service processes or model downloads.

## Services and architecture

### The service contracts

All files below declare OpenAPI **3.1.0** and contract version **1.7.1**.

| Contract | Responsibility | Main resources and operations |
| --- | --- | --- |
| [Event](openapi/opal_event.yaml) | Event publication, routing, and registered action execution | Event ingress/history, topics, rules, shell/HTTP/Python actions, execution records, statistics |
| [Listen](openapi/opal_listen.yaml) | Wakewords, speech-to-text (STT), intent recognition, and slot extraction | Recognition start/stop/status/stream, text/audio diagnostics, intents and phrases, slots and aliases, regression cases, failed utterances, performance |
| [Look](openapi/opal_look.yaml) | Visual observation: video-only or inference RTSP streams | Optional engine discovery (YOLO, RF-DETR, RT-DETR, D-FINE adapters), engine-owned models, single-image prediction, engine-local hardware, ephemeral stream sessions with SSE metadata, MJPEG viewing, snapshots, and metrics |
| [Say](openapi/opal_say.yaml) | Text-to-speech (TTS) over host-installed engines | Engine discovery/configuration, voice registration and validation, completed audio generation, progressive PCM streaming |
| [Think](openapi/opal_think.yaml) | Bounded reasoning work using configured models and Event actions | Asynchronous tasks, progress/output streams, cancellation, optional conversation sessions, model discovery |
| [Shared kernel](openapi/shared/opal_kernel.yaml) | Common contract building blocks | Parameters, response headers, error responses, schemas, reusable Path Items, and suite extensions |

The shared kernel has no public routes of its own (`paths: {}`). Service documents mount reusable **Path Items**—OpenAPI definitions of operations at a path—and reference common components through external `$ref` links.

```text
openapi/shared/opal_kernel.yaml
            |
            | external $ref references
            v
openapi/opal_{event,listen,look,say,think}.yaml
            |
            +--> Redocly and Spectral validation
            +--> Python contract assertions
            |
            +--> npm run bundle --> dist/opal_*.yaml
                                    standalone consumer documents
```

### How services cooperate

Listen can publish live microphone intent matches. Event routes matching events to registered actions. An HTTP action can submit a task to Think; Think can in turn discover and invoke Event actions through REST.

```text
Listen -- live intent events --> Event -- registered HTTP action --> Think
                                     ^                                  |
                                     +-- action discovery/execution ----+
```

Event owns the action definitions and execution records. Its `think` principal has `actions:read`, `actions:execute`, and `executions:read` permissions, with configuration write scopes explicitly denied. Action definitions can include a description, keywords, suggested prompts, and a JSON Schema describing `EventInput.data`.

Several distinctions matter when building integrations:

- **Admission is not completion.** Event publication and action execution use `202 Accepted`. Think task creation also returns `202`, with a durable task ID and `Location`. Consumers inspect the appropriate task or execution record for the result.
- **Events are best effort.** The contract does not promise delivery, ordering, automatic retries, or exactly-once side effects. Listen's external publication is disabled by default; diagnostic text/audio requests never publish actionable events. Look has no event-bus surface in the MVP Plus contract.
- **Streams have different guarantees.** Look stream Server-Sent Events (SSE) support bounded replay with `Last-Event-ID`; Think task SSE has no guaranteed replay, and the final task snapshot remains authoritative. Say streams raw signed 16-bit little-endian mono PCM audio.
- **Capabilities can be optional.** Look's inference engines are optional discoverable adapters — video-only streams work with zero installed engines. Say engines and voice resources are installed on the host; its API registers and uses them rather than downloading models. Say returns audio bytes; playback is outside its API.

## Installation and quickstart

Clone the repository and install the Node tooling:

```bash
git clone https://github.com/PatMartin/opal-api.git
cd opal-api
npm ci
python -m venv .venv
```

Activate the Python environment using the command for your shell.

**Bash or zsh on Linux/macOS:**

```bash
source .venv/bin/activate
```

**PowerShell on Windows:**

```powershell
.\.venv\Scripts\Activate.ps1
```

**Git Bash on Windows:**

```bash
source .venv/Scripts/activate
```

Then install the Python dependencies and run the complete check:

```bash
python -m pip install -r requirements.txt
npm run check
```

The successful end-to-end result is an exit status of `0`, passing contract assertions, and five bundled YAML documents under `dist/`. Lint warnings can still appear on a successful run.

There is no server start command for this repository. Its executable workflow is validation and bundling; the `service/start` API routes describe behavior for service implementations.

## Working with the contracts

### Validate and build consumer artifacts

For a quick structural check followed by bundle generation:

```bash
npm run validate
npm run bundle
```

The bundle script writes:

```text
dist/opal_event.yaml
dist/opal_listen.yaml
dist/opal_look.yaml
dist/opal_say.yaml
dist/opal_think.yaml
```

Each bundle incorporates external kernel references into a single document suitable for OpenAPI viewers and downstream tooling. Internal references can remain: the script uses Redocly `bundle` without its `--dereferenced` option. These files are build artifacts, not separately maintained source specifications.

### Inspect a resolved operation

The test helper resolves local and shared-base references and copies path-level CLI mappings onto the corresponding operations. From the repository root, run:

```bash
python -c "import sys; sys.path.insert(0, 'tests'); import spec_util; d = spec_util.load('openapi/opal_think.yaml'); print(d['info']['title'], d['info']['version']); print(d['paths']['/api/v1/task/']['post']['x-opal-cli'])"
```

Expected output:

```text
OPAL Think API 1.7.1
{'group': 'task', 'command': 'create', 'aliases': ['ask', 'chat']}
```

[`tests/spec_util.py`](tests/spec_util.py) is a repository-specific test utility. Use the generated bundles when a consumer needs a portable standalone OpenAPI document.

### Understand CLI metadata

The kernel's `x-opal-cli-format` extension defines the mapping:

```text
opal <service> [parent] [group] <command>
```

For example, Think's task creation operation declares:

```yaml
x-opal-cli:
  group: task
  command: create
  aliases:
  - ask
  - chat
```

Descriptors have a required `command` and optional `parent`, `group`, and `aliases`. Kernel-mounted paths attach a per-method map beside their `$ref`; the test helper hoists that map onto operations for assertions.

Look and Think currently annotate all their operations. Event, Listen, and Say have partial annotation coverage. The general Spectral rules validate descriptor shape where annotations exist, while the Look parity test explicitly checks operation coverage and command uniqueness.

The [cookbook](docs/COOKBOOK.md) describes the intended unified Typer CLI, a Python command-line interface, and its workflows. This repository supplies metadata and documentation; installing its dependencies does not install an `opal` executable.

## Shared API conventions

The kernel describes **OPAL Suite Standard v1.2**. This standard version is distinct from the files' `info.version` values, the OpenAPI format version, and event metadata versions. The private npm package's `1.0.0` version identifies the tooling package rather than the API contract.

### Routes and common management

Routes use `/api/v1`, singular resource names, and trailing slashes on collection roots, such as `/api/v1/task/`. All five services expose these common families, except where noted:

| Family | Contract surface |
| --- | --- |
| Identity | `GET /api/v1/info/`, `GET /api/v1/info/ping` |
| Health | `GET /api/v1/health/`, `/api/v1/health/live`, `/api/v1/health/ready` |
| Settings | `GET`/`PATCH /api/v1/setting/`; `GET`/`PUT`/`DELETE /api/v1/setting/{key}` |
| Profiles | Collection and item CRUD (create, read, update, delete), plus activation |
| Personas | Collection and item CRUD, plus service-local binding validation (Event, Listen, Say, and Think; Look has no persona surface in the MVP Plus contract) |
| Backups | List, create, download, delete, export, import, restore, and validation |
| Service lifecycle | `POST /api/v1/service/start`, `POST /api/v1/service/stop`, `GET /api/v1/service/log` |

Say and Look also expose engine listing and item read/update operations. Listen and Say additionally allow `GET /api/v1/backup/validate` to validate staged configuration; all five expose the POST validation operation. Persona operations are defined in each media service using shared schemas rather than mounted kernel Path Items.

### Correlation, concurrency, and errors

- **Correlation:** `X-Opal-Session-Id`, `X-Opal-Transaction-Id`, `X-Opal-Request-Id`, and `X-Opal-Causation-Id` carry context. Request and transaction response IDs are required; session and causation IDs are conditional. A trace session ID does not itself create a service-managed session.
- **Configuration revisions:** strong ETags identify portable configuration revisions. Configuration mutations require an exact strong `If-Match` validator: missing is `428`, stale is `412`, and malformed is specified as `422`. Runtime admissions and data operations have their own concurrency rules.
- **HTTP outcomes:** resource creation uses `201` with `Location`; asynchronous admission uses `202`; empty deletion uses `204`. Consult the operation for its exact response headers and statuses.
- **Errors:** JSON error responses use the `OpalError` envelope. Health probes are a deliberate exception: their `503` response uses a `status`/`ready` health body.
- **Collections:** bounded configuration catalogs return full arrays, subject to deployment caps. Histories use bounded arrays and `limit`, with operation-specific ordering. The contracts do not expose cursor pagination.
- **Authentication:** non-loopback deployments require authentication; loopback deployments may explicitly disable it. `401` means missing or invalid credentials and `403` means insufficient permission. Correlation IDs never grant access.

The event envelope extension describes two ZeroMQ frames: a topic and a JSON envelope. Optional correlation metadata lives under `data.metadata`, and consumers must ignore unknown metadata fields.

### Profiles and personas

A **profile** is a named preset of a service's operating defaults. A **persona** is an identity that can carry service-specific bindings, such as a Say voice. The kernel defines per-field resolution as:

```text
explicit request field > persona binding > profile > service default
```

The ownership contract names Think as the authoritative persona registry. Services can keep local records for standalone use or fetch and revalidate owner records when an owner URL is configured. Each service's persona validation reports its own binding resolvability. The concrete request schemas determine which bindings and selectors a service accepts.

## Configuration

### Repository tooling

No application environment variables or secret configuration are required for the checks. The validation tools read these repository files:

| File | Role |
| --- | --- |
| [redocly.yaml](redocly.yaml) | OpenAPI structural checks using Redocly's recommended rules |
| [.spectral.yaml](.spectral.yaml) | Generic OpenAPI linting |
| [.spectral.opal.yaml](.spectral.opal.yaml) | Suite conventions, including correlation headers, error shapes, creation headers, and CLI descriptor format |
| [.spectral.opal.look.yaml](.spectral.opal.look.yaml) | Look-specific concurrency, health, and event-contract checks |
| [.spectral.opal.think.yaml](.spectral.opal.think.yaml) | Think-specific concurrency and health checks |

Trailing-slash lint rules are disabled because the suite requires collection trailing slashes. Spectral's `oas3-schema` rule is disabled for the external Path Item reference issue documented in the rulesets; Redocly still performs structural validation. Redocly's `security-defined` rule is also disabled, while the Python security suite checks the explicit authentication declarations.

### Service configuration described by the APIs

Actual service deployment configuration belongs to the implementations. At the contract level:

- Settings use native JSON values. Collection PATCH is atomic; deleting a per-key override restores the implementation default.
- Configuration exports omit secrets and history. Import and restore validate before atomic application and require `If-Match`.
- Credential references such as `token_env` and Think provider `credential_ref` identify configured secrets; secret values must not be returned.
- The shared service-start options default `append` to `false`, truncating `logs/opal_<service>.log`; log retrieval defaults to 10 trailing lines.

Check each spec's `info.description`, request schemas, and extensions for service-specific settings and limits. Server URLs in the specs are local examples, not a deployment plan for running all five services on one machine.

## Validation and tests

All commands run from the repository root. The Node CLIs are installed locally by `npm ci`; global installations are unnecessary.

| Command | Purpose |
| --- | --- |
| `npm run validate` | Redocly structural linting and reference resolution for the five service specs |
| `npm run lint` | Generic Spectral OpenAPI rules |
| `npm run lint:opal` | Suite Spectral rules on service specs |
| `npm run lint:kernel` | Suite Spectral rules directly on the kernel |
| `npm run lint:look` | Look-specific Spectral rules |
| `npm run lint:think` | Think-specific Spectral rules |
| `npm run bundle` | Build the five standalone documents in `dist/` |
| `npm run test:lint` | Mutate temporary spec copies and check that selected lint rules report the expected findings |
| `npm run test:event150` | Event action metadata, JSON Schema fixtures, references, input validation semantics, permissions, and settings |
| `npm run test:think-event` | Declared Think/Event scopes, integration routes, admission semantics, and execution states |
| `npm run test:look-cli` | Look operation CLI mappings and selected operational routes, parameters, and error declarations |
| `npm run test:listen150` | Listen native JSON settings and concurrency preconditions |
| `npm run test:say150` | Say import/restore preconditions and atomicity declarations |
| `npm run test:rest-security` | Bearer authentication declarations, suite authorization semantics, and `401`/`403` response coverage |
| `npm run check` | Run all 14 stages above, stopping at the first failing command |

The `150` script/file names are historical; those suites load the current contracts and assert version `1.7.1`. Tests inspect schemas and declarations rather than sending requests to running services. A passing suite does not establish runtime conformance or prove every behavioral requirement.

The [GitHub Actions workflow](.github/workflows/openapi-validate.yml) runs the same set of checks on Ubuntu with Node 22 and Python `3.x`. Unlike the local `&&` chain, CI runs validation stages with `continue-on-error` and aggregates their outcomes. It runs for pull requests, manual dispatches, and pushes to `main`, `integration/**`, and `proposal/**`.

Spectral warnings are non-blocking under the current commands; error findings fail the check. Read warnings when changing related areas rather than treating a successful exit as a warning-free result.

### Troubleshooting

| Symptom | What to check |
| --- | --- |
| Redocly reports an unsupported engine | Check `node --version` and `npm --version` against the requirements above |
| Python cannot import `yaml` or `jsonschema` | Activate the intended environment and run `python -m pip install -r requirements.txt` |
| Lint regression tests cannot find Spectral | Run `npm ci`; the harness prefers `node_modules/.bin/spectral` or `spectral.cmd` |
| A new kernel reference does not resolve | Check the reference path and fragment, then run `npm run validate` and `npm run bundle` |
| `npm run check` stops before a later test | Fix the failing stage, or use that later stage's individual npm command to inspect it |

## Development and contributing

1. **Read the relevant contract and nearby tests.** Start with the service's `info.description`, its operation schemas, and the shared kernel. Check both structured definitions and prose when changing behavior.
2. **Choose the right source location.** Keep service-specific schemas in the service spec. Add reusable components to the kernel and reference them with paths such as `./shared/opal_kernel.yaml#/components/schemas/OpalError`. Shared edits can affect every service.
3. **Preserve interface conventions.** Review correlation parameters and response headers, authorization errors, error envelopes, item-not-found responses, configuration preconditions, creation headers, and CLI metadata where applicable.
4. **Extend meaningful coverage.** Reuse the matching Python test file. Event action payload fixtures belong in `tests/fixtures/event_150/`; new lint guarantees should have a mutation case in `tests/test_lint.py`. Use `spec_util.load` when assertions need the resolved contract.
5. **Review compatibility and documentation.** Changes to required fields, routes, response types, operation IDs, or CLI bindings can affect clients. Update affected descriptions, examples, version assertions, and cookbook material when revising the published contract.
6. **Run `npm run check` and review the diff.** Generated `dist/` files stay ignored. Submit source changes and relevant documentation/tests in a pull request.

The repository has no configured formatter or type-checker command. Follow nearby YAML and Python style and use the validation commands above.

Existing branches and CI support `proposal/<topic>` and `integration/<topic>` naming. The history contains both plain descriptive commits and prefixed subjects; no mandatory commit-message format is configured. Pull requests should explain the concrete contract change, compatibility implications, and validation results.

The security test also scans `openapi/proposals/*.yaml`, but most validation scripts target only `openapi/*.yaml`. If a change introduces a new contract location, update the relevant script and test inputs so its intended coverage is explicit.
